# Report Implementation Guidelines

Use this checklist when adding any new report to keep behavior and UX consistent.

## 1) Standard Report Layout

- Use the same visual structure as current reports:
  - Header with report title + short description.
  - Actions in header: `Print` and `Download CSV` only (unless explicitly required otherwise).
  - Filter block in a bordered section.
  - Main results table with compact report styling.
  - `Report Generation Details` card shown after data is generated (and optionally repeated at bottom).

## 2) Report Generation Details (Required)

Include a card with:
- Filter summary used for this run.
- Generated by (formatted user display name).
- Generated at (local date-time).

Keep style consistent with existing report meta cards:
- Primary tinted background
- Left border accent
- Small uppercase labels

## 3) Date / Date-Time Range Rules

- If report is date-only:
  - Use date range picker.
  - Backend must interpret as inclusive full-day:
    - from = `00:00:00.000`
    - to = `23:59:59.999`
- If report needs time precision:
  - Use date-time range picker.
  - Preserve selected from/to time exactly.

Always validate:
- both values are present
- from <= to

## 4) Query Safety Guards (Required for heavy reports)

Use shared helpers from:
- `lib/report-limits.ts`

Available helpers:
- `getReportMaxRangeDays(reportKey, fallback)`
- `getReportMaxRecords(reportKey, fallback)`
- `getInclusiveDaySpan(from, to)`

Recommended guard flow:
1. Validate date range.
2. Enforce max day span.
3. Run lightweight `count` with same filters.
4. Reject if over max records with a user-friendly message.
5. Only then run heavy `findMany` + aggregation.

## 5) Environment Variables for Report Limits

Two-level configuration is supported:

1) Global defaults:
- `REPORT_MAX_RANGE_DAYS`
- `REPORT_MAX_RECORDS`

2) Per-report overrides:
- `REPORT_<REPORT_KEY>_MAX_RANGE_DAYS`
- `REPORT_<REPORT_KEY>_MAX_RECORDS`

Examples:
- `REPORT_DOCTOR_APPOINTMENT_COUNT_MAX_RANGE_DAYS`
- `REPORT_DOCTOR_APPOINTMENT_COUNT_MAX_RECORDS`
- `REPORT_ALL_CASHIER_SUMMARY_DETAIL_MAX_RANGE_DAYS`
- `REPORT_ALL_CASHIER_SUMMARY_DETAIL_MAX_RECORDS`

Priority:
1. Per-report override
2. Global default
3. Code fallback

## 6) Filter UX Rules

- Avoid duplicate "All ..." entries inside dropdown option lists when default label already represents all.
- For async/late option lists:
  - Show loading indicator only while options are not ready.
  - Do not tie dropdown loading indicator to report-search loading.
- Disable Search while required filter options are still loading.

## 7) Table Conventions

- Use compact report table classes:
  - small font (`text-[11px]`)
  - right borders on cells
  - tabular nums for numeric columns
- Keep count columns centered when requested.
- Keep monetary columns right-aligned by default.
- Make totals row visually stronger (`font-semibold` and muted background).

## 8) Export / Print Rules

- CSV export should match visible columns and formatting intent.
- Include totals row in CSV when table includes totals.
- Use report-specific file naming:
  - `<report-slug>-YYYY-MM-DD.csv`

## 9) Validation / Error Messages

Return clear, actionable messages:
- invalid dates
- range too large
- too many records (ask user to narrow date/filter)

## 10) Performance Notes

- Prefer DB filtering first; avoid loading unnecessary relations.
- Use `count` guard before expensive queries.
- Avoid unbounded queries on receipt/booking heavy reports.
- Reuse shared formatting helpers (`formatUserDisplayName`, money formatters) for consistency.
